# Decision Record

A chronological record of the major decisions made across planning, kept
here so the reasoning behind each is stated plainly and stays traceable
in the final report. Terms in *italics* are defined in the
[glossary](glossary.md) the first time they appear.

| Decision | Reasoning |
|---|---|
| This project chosen as the topic | A tighter fit for a cybersecurity department; a narrower, more measurable research question; an already-designed peer-to-peer network layout carries over directly onto the hardest part of this project. |
| Test plan scaled down from 3 comparison systems / 50 nodes / 7 attack scenarios to 2 working systems / 4 to 8 nodes / 3 attack scenarios | Fits an October to January timeline; the original plan was closer to 6 to 12 months of work. |
| A second contribution (automated classification) added alongside trust-checking | Research confirmed CERT-GH's own sorting step is done entirely by hand, with no automated help anywhere in it, a real, documented gap. |
| VLAI (an existing pretrained severity-scoring model) set aside as the classifier's starting point | Two reasons together: VLAI is trained on vulnerability-description text, a different kind of input from the traffic and log data this project classifies, so it would not have worked; and training a new model from labeled data built specifically for this project makes the contribution clearly original work. |
| Classifier built as a self-trained *[gradient-boosted-trees](glossary.md#gradient-boosted-trees)* model over a small set of hand-picked measurements | Matches the realistic amount of training data available and the project timeline; trains quickly enough to iterate on; and its decisions can be inspected, which helps both the write-up and a reviewer's trust in a given result. |
| *[OpenCTI](glossary.md#opencti)* used as the storage/display sink this project tests against | Keeps the limited build time focused on this project's two genuinely new pieces; OpenCTI is actively maintained, and installing it as an external dependency sidesteps needing to reason about its own license at all. |
| OpenCTI evaluated against *[MISP](glossary.md#misp)* before choosing | MISP's way of recording independent sightings of the same indicator, and its built-in message signing, were noted as useful reference points. OpenCTI's active development and its way of storing relationships between records made it the right fit for this project. |
| The Peer Validation Layer and the classifier built as their own separate programs calling OpenCTI | Keeps this project's own original work clearly separate from any downstream platform, both for license clarity and for how the work will be examined. |
| Rust chosen for the Peer Validation Layer; Python chosen for the classifier | Rust's speed and low-level control suit the networking and message-signing work; Python's mature machine-learning tools suit the classifier. Neither sits inside OpenCTI's own code, which is written in TypeScript/JavaScript with some Python and Node used for its own connectors. |
| Reading and gathering citations left until closer to report-writing time | Matches an established working pattern of building first and reading deeply right before the sections that need those citations; the design and feasibility groundwork was already complete. |
| Standing up OpenCTI moved earlier, run in parallel with the first pipeline milestone | The week-by-week roadmap table never actually assigned a week to forking or deploying OpenCTI, a real gap noticed only once work was underway. The classifier and the step that pushes believed observations into it both need OpenCTI running, so closing the gap early kept it from surfacing later as a blocker. |
| OpenCTI deployed inside the local test VM | The host had already shown real memory pressure earlier the same session during much lighter work; isolating OpenCTI's own dependency stack (search index, message queue, object storage) inside the VM kept that risk contained to one place. |
| An earlier fork of OpenCTI's repository (`DevInBlack001/opencti`) dropped; OpenCTI treated from then on as an external dependency installed straight from Filigran's own official channel | Reading OpenCTI's own license file directly found its public repository carries two different licenses: Community Edition under Apache 2.0, and a separate, much larger set of Enterprise Edition features under a far more restrictive license that, without a paid or research/nonprofit license key from Filigran, forbids public distribution, hosting for third parties, or merging into another product. The deployment had always pulled the plain public Docker Hub image (`deploy/docker-compose.yml`), so dropping the fork removed real distribution risk while keeping the whole five-layer architecture, the roadmap, and the running VM deployment unchanged. |
| The Local Collection Layer built via subagent-driven development: a fresh implementer and an independent review per task, across 9 tasks, plus a dedicated security review and a final whole-branch review before merging | The 9-task plan was well-specified enough for isolated, independently-testable pieces; per-task review catches most issues immediately, but a dedicated security pass and a final whole-branch pass each caught real issues no per-task review could have found alone (a SQLite URI injection bypassing a symlink guard, a sink file with no symlink guard at all, and a side-effect ordering bug that minted a permanent node identity even on a run that failed to read its source), confirming both passes earned their own place in the process. |
| Brute-force upgraded to a real, live-simulated attack scenario in the VM testbed, matching DDoS; phishing kept as sample data, generated fresh by a script at test time | The VM testbed (attacker, crowd, victim, gateway) already exists to support DDoS, so extending it to a real brute-force scenario is a small addition. Full phishing infrastructure (a real mail server, a corpus of real phishing messages) would be a disproportionately large build for one demo scenario. A hardcoded sample-data fixture was rejected outright: anyone cloning the repository could see exactly what the "test data" looks like, undermining both the demo and the project's own no-hardcoded-values rule extended to test data. |
| The future sink connector layer designed for multiple simultaneous sinks from the start, including peer nodes alongside downstream platforms | Nothing has been built against the sink interface yet (the current pipeline only writes to a local file), so building fan-out in now costs nothing extra. A believed observation should reach every configured destination at once, a node's platform or platforms and its peers together. |
| Scope for the sink connector layer's first real implementations set to OpenCTI and Wazuh | This project holds every connector to one standard: built and verified against the real thing (FLOD's own connector was built by reading its actual schema). OpenCTI already runs in this project's own test VM; a real Wazuh server, reachable for the same treatment, exists in the author's own homelab. Closed and proprietary platforms have no such access available, so building connectors for them now would mean unverified code, off the standard already held everywhere else in this project. |
| Wazuh added as both a source and a sink connector | As a source, Wazuh's own alerts are a stronger long-term local-detection input for real institutions, since it is a real, widely-deployed open source SIEM many resource-constrained organizations already run. As a sink, its active-response mechanism is a natural place for the Local Action layer to act on confirmed intelligence. |
| Sink connector work (OpenCTI, Wazuh) and the Wazuh source connector scheduled in parallel with the Federation Layer | Neither piece structurally depends on Federation existing; a sink connector only needs an already-signed Threat Observation, which Task 4 already produces. Federation stays the priority build, since it is both the original schedule and the layer this project's actual research contribution depends on. |
| The node dashboard moved from week 10 to week 9, alongside Local Action and reputation scoring v2 | Its main view is peer network status and classifier performance; week 9 is the earliest point Federation and Peer Validation have both produced real data for it to show. The classifier itself has no dedicated build week on the current roadmap yet, a gap worth noting here; the dashboard degrades gracefully on classifier metrics until that piece exists. |
| A minimalist per-node dashboard added to the roadmap, separate from any CTI platform's own browsing UI | A downstream platform like OpenCTI has no way to show this project's own actual contribution (reputation scores changing over time, which quorum decisions went which way, attack-scenario results), since that data is specific to this project's own layers. Kept deliberately minimal, with a link out to the node's CTI platform for anyone who wants full browsing. |
| The Federation Layer carries reports in this project's own format only | Keeps peer-to-peer sharing independent of which CTI platform each node happens to run locally; a node on OpenCTI and a node on MISP exchange reports the same way, since translating into a specific platform's format is the sink connector's own job, a separate step handled after a report is received. |
| A single attestation server planned for peer onboarding, with no other role | New peers need some way to be checked before joining; giving that job to a dedicated, narrowly-scoped server keeps it from becoming a dependency for anything else. Already-validated peers keep exchanging and validating reports directly with each other, so the attestation server going down only stops new peers from joining. |
| Zero trust adopted continuously between peers, from onboarding onward | Passing attestation once is a one-time check at the moment a peer joins. Verifying every message on its own signature and content, and letting the reputation-weighted quorum keep recalculating trust from actual, ongoing track record, means a peer's network location or past success is never substituted for checking the message actually in front of a node. |
